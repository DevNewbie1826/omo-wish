$ARGUMENTS

Use ultrawork explore to analyze the overall context and history of the work and assess the current problems and key decision points based on evidence. Identify everyone and everything the result touches and affects; end customers, other developers, and code that depends on the result are all included. Think deeply about how they use it now, how they will use it, and what problems and pain points they face. Logically define the ideal state, where those problems are solved and they hit no friction, nothing feels wrong, and no regression or degraded experience occurs, and make it one concrete top-level goal. List every gap between the ideal state and the current state. Before implementing, define QA scenarios from their perspective that prove the ideal state is reached, based on each gap and every point where they could get stuck, and register them as the ulw loop's success criteria. This goal, the gap list, the QA scenarios, and the execution principles below MUST remain the governing criteria until the entire work is complete. Continue until the result matches the ideal state exactly. NEVER narrow the scope or weaken the criteria or scenarios to finish the work. NEVER leave a gap open with an excuse such as "pre-existing", "out of scope", or "follow-up". Ask the user instead of deciding alone on anything only the user can decide. Add gaps discovered during the work to the list, create matching QA scenarios, and treat them exactly like the original list.

Apply the system-provided tool execution and eval policies consistently throughout the entire run.

Run the whole work as one ulw loop with this one top-level goal. Tasks are execution units inside it; do not register them as separate ulw-loop goals. Handle one requested piece of work as one task; each task is one worktree, one PR, and one DAG. Do not split gaps into tasks; split them into nodes inside that task's DAG. Create a separate task only when this session has work with a different purpose. Two tasks are independent when neither can affect the other's correctness; when independence is unclear, keep them in one task. Run the DAGs of independent tasks concurrently, not one after another, and start a dependent task only after its prerequisite task is merged.

For each task, MUST create a dedicated Git worktree and use mass ulw to construct a DAG around the work and its actual dependencies. In every DAG, including REVISE DAGs, split the work into independent nodes wherever correctness allows. Run independent nodes in parallel with disjoint write scopes, and dependent nodes in order. The DAG MUST end with combined verification including the task's QA scenarios -> PR creation -> ultrabrain review, in that order. The ultrabrain review MUST end with APPROVED or REVISE and list required changes on REVISE.

On REVISE, MUST build the next mass ulw DAG in the same worktree from the required changes. Run independent fixes in parallel, verify the combined result including the task's QA scenarios, and have ultrabrain re-review as the final node. Repeat until APPROVED.

NEVER merge a PR before ultrabrain gives APPROVED. Merge approved tasks one at a time without waiting for unrelated tasks. When integration with other changes affects a task's behavior, re-verify only the affected behavior and reuse results that remain valid. If the approved implementation changes substantively in the process, have ultrabrain re-review it before merging. Once all tasks are merged, confirm that every QA scenario passes on the merged result, again reusing valid results and rerunning only the scenarios the merges affected. If any scenario fails, make its cause a fix task and handle it through the same flow. Once the original top-level goal is fully satisfied, remove the task worktrees and merged task branches used for this work, then complete the ulw loop.

Always respond in the user's language.
