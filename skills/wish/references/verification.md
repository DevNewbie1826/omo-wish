# wish: verification, PR, review, and merge

This file covers stage 3, plus the checks the batch verification nodes run in stage 2. Define these closing nodes when you define the task DAG in stage 2, before the DAG starts; they run after the production nodes settle (`SKILL.md`, Stages and required reads).

## Batch verification checks

Each batch verification node (`references/execution.md`, Worktree and node design) runs these checks in addition to the VERIFY reruns that `references/execution.md`, Worktree and node design, requires, and its verdict names every finding:

- **Defect classes.** Answer the question of each class the plan chose whose Checked at column in `references/planning.md`, Defect classes, says Batch verification, against the batch's output.
- **Mutation check.** When the batch changes testable runtime behavior, pick the three to five highest-risk changed behaviors, or all of them when fewer than three changed. For each, break the production code with one small edit in a throwaway copy of the worktree, run the tests that should guard it, and record the result as killed (a test failed) or survived (none did). A survivor is a finding for the node that owns that behavior. Behaviors covered by a valid `no-test` row, including every change in a prose-only batch, get no production mutation; the verdict records that and why, and they follow Combined verification. This is a bounded sample, not a full mutation-testing run.

## Combined verification

Run the task's QA scenarios through their real surfaces, plus the tests the repository keeps for the changed behavior. Tests alone don't prove the user-visible behavior; each scenario needs its own artifact. Record the command, the observable, PASS or FAIL, and cleanup receipts for anything the QA started. Assert the identity and marker of each record, not only its count: totals can hold steady while records change or vanish, and a locator that can match an aggregate checks the aggregate. Record the reference set by identifier and marker, and diff that. Every artifact a verdict, conformance row, or PR body cites must exist at the cited path when cited and show the observable itself, uncropped. A record never retypes a measured value, such as a SHA, a count, a size, a computed table cell, or a revision: it cites the path of the capture that holds the value, with the identifier of the run that wrote that capture, or the value appears only in output that the measuring command or script wrote. A narrative report is a reading aid; a claim in it counts only through the capture it cites.

A QA comparator or harness is evidence only when it fails closed. Run it once on a corrupted or missing input as a control and capture that failure beside its passing run. A comparator seen only passing, or one that still passes with an input missing, is invalid evidence. The control must go through the same comparison as the passing run: a control that would still pass with that comparison replaced by a constant is tautological and isn't a control.

Before the PR opens, the combined verification node runs the skill's evidence lint, `scripts/evidence-lint.mjs` in this skill's directory, over its run's evidence directory and captures the output. That directory holds every verdict, the conformance table, `reuse.md`, and the PR-body draft `<evidenceRoot>/<run-key>/pr-body-draft.md`; the lint lists every file it scanned, and the capture must list the draft. Every cited path must exist, every 40-hex value must be a commit that appears in a capture, every `file:line` citation must hold the text it quotes, and every comparator capture must have a failing control capture beside it. A lint failure is a mismatch, fixed in the same worktree before the PR. The lint is never edited during a run: a defect in it is a follow-up record, and the run continues with the manual checks this paragraph replaces, named in the verdict. The PR node uploads the draft as the PR body unchanged; nobody retypes its contents.

Then check the plan's risk list:

- Every `guard` row: its test exists and passes, and its injection check shows the injection diff, the failing output, and the passing output after restore, with the diff producing the regression the guard names.
- Every `no-test` row: the reason is one of the allowed ones, and any QA scenario it names passed. Check each claim the row makes against the source it cites, and record that check, with the file and line, as evidence; a claim with no source, or one the source doesn't establish, is invalid evidence.

A missing guard test, a missing capture, an injection diff that doesn't produce the guard's regression, an injection that stayed green, a scenario that skipped a step it claims (`references/planning.md`, The plan, QA scenarios from the users' side), or a `no-test` reason outside the list is invalid evidence. A touched behavior missing from the risk list is in scope when it shows an IS or COMPANION row not delivered, when this change introduced a regression, or when it passes companion guards (a)-(c) (`SKILL.md`, The purpose boundary): add the COMPANION row and fix it in the same worktree. Otherwise it is a follow-up note (`SKILL.md`, Follow-up record).

If a scenario fails, it's in scope by definition. Fix it in the same worktree before opening the PR.

Then build the **conformance table**, one row per IS row of the plan, with these columns: the IS row; `GAP` with the gap it closed, or `no gap` with the evidence it was already met; the todo that closed it; the QA evidence path with `PASS` or `FAIL`; and the `guard` row that protects it, or `none`. A row whose evidence is missing or failed is a mismatch: fix it in the same worktree, then refill the table. The PR opens only when every row matches. If an IS row itself proves wrong, such as a wrong party or rows that contradict, fix only that row in the plan and record why; **NEVER** restart the run for it.

## Evidence reuse per target

Evidence is valid for a target (a scenario, test, or review claim) until something it depends on changes. Before reusing it:

1. Check what changed since capture: the files it exercised, its dependencies, and the environment it ran in. At minimum, treat as affected the tests of every file the change touched and of the files that import it, and the scenarios that exercise them.
   Count the comparator, harness, or script that produced the evidence as one of its dependencies. When a change touches only that tool, rerun the targets whose verdict the change can alter and re-capture the tool's corrupted-input control beside them; targets whose code path in the tool is unchanged keep their evidence. When you can't tell which targets the change alters, rerun all of them.
2. If none of those changed, reuse it. Keep the original capture's provenance (when, where, which commit) and write down why it's still valid.
   Every capture records the sha256 of each file it depends on, including the producing tool, as `shasum -a 256` output. The combined verification node writes `reuse.md` beside the verdicts: one row per target with its capture path, its dependencies, each dependency's sha256 as recorded at capture and as computed now (both as command output, never retyped), and `reuse` or `rerun`. Reviewers receive `reuse.md` with the diff and read the listed captures instead of rerunning those targets; a reviewer that reruns a `reuse` row states why in its verdict.
3. If any changed, or you can't tell, rerun that target.

Never overwrite or delete a captured artifact. Write each rerun to a new file suffixed with its attempt number and keep every earlier one. A verdict file the gate reads at its fixed path (`references/execution.md`, Worktree and node design) is the one exception: it carries no suffix.

When the lead re-checks a capture, it runs the producing script against a copy or a new output path; rerunning it in place overwrites the capture this rule protects.

Don't invalidate all evidence because one file changed, and don't rerun the full matrix after every patch. The one full pass happens before the final report (see Merge and finish).

## PR

Follow `SKILL.md` rule 6 and Task shape for PR timing and shape. The body lists the behavior delivered, the tests and QA run, and the real limits. It also carries the conformance table from Combined verification and the plan's COMPANION rows. No blanket enforcement claims.

## Final ultrabrain review

After the PR exists, spawn one review with `category: "ultrabrain"`. Follow `SKILL.md`, Delegation prompts, and pass the diff, the goal and criteria, the plan's risk list, the conformance table, the plan's Plan review record (`references/planning.md`, Plan review), and the QA artifacts. The review covers the whole change to the end and reports every defect it finds in one verdict. It **NEVER** stops at the first defect to return REVISE, and a REVISE that leaves the rest of the change for a rerun to find is prohibited. For each defect it names the defect class and gives one minimal reproduction: the input, the command, and the observed output. It may test variants of a defect itself, but it isn't required to, because the variant sweep in REVISE, step 2, does that. The review checks the plan-review blocker fixes. It also answers each class in `references/planning.md`, Defect classes, whose Checked at column says Final review, for the docs, the PR body, and the reports. It ends with APPROVED or REVISE. On REVISE it lists required changes, and each one must show goal failure (`SKILL.md`, Delegation prompts), an introduced regression, or invalid evidence, including risk-list evidence that fails the Combined verification check; an item that passes companion guards (a)-(c) (`SKILL.md`, The purpose boundary) counts as goal failure. Anything else it raises is a follow-up note. Each required change also carries `layer: PRODUCT` or `layer: EVIDENCE` and the file:line it rests on; `layer: EVIDENCE` means the change touches only the run's own records, such as captures, verdicts, reports, and the PR body, and none of the task's files. A doc mismatch's reproduction is the two quoted lines that contradict each other. Before a correction run starts, the lead runs each reproduction once and captures the result; a required change whose reproduction doesn't reproduce is still fixed, and that capture records it.

This review is mandatory and isn't replaced by anything below.

## Loop checkpoint gate

The ulw-loop final checkpoint may require a quality-gate record whose reviewer field accepts only certain category literals. If `ultrabrain` isn't accepted there, run one separate audit with an accepted category (the checkpoint doc lists them). Bound it to checking that the evidence exists, matches the criteria, and fits the schema. It isn't a second product review, and it doesn't reopen the ultrabrain verdict.

## REVISE

1. Follow `SKILL.md`, Task shape and Stages and required reads, for the correction run's worktree and PR.
2. Build a new mass-ulw correction run from the required changes, under `SKILL.md` rule 4. Record each required change's cause class in the loop ledger, as for any work failure (`references/execution.md`, Recovery). The run fixes each required change as the defect class it represents, not only the instance or wording it cites, in three stages:
   1. **Variant sweep.** One sweep node per required change the verdict reports, all in parallel, each routed by its class's difficulty: a simple class to a cheaper category, a complex one to a higher-capability category from the host's list (`references/execution.md`, Worktree and node design). The node receives that required change's class name and its one minimal reproduction. It reads the code and writes down the axes along which inputs of that class can vary, such as, for a numeric input, very large, zero, negative, whitespace-mixed, unicode digits, empty, and near-limit values. For a defect with no input variants, such as a doc or design mismatch, the axes are the other places or occurrences where the same class can appear. For each axis it runs representative inputs, both extremes and the boundary values, against the real entry point; running them is the test. It groups the failures by root cause. When a full pass over every axis finds no new root cause, the node stops; when a pass finds a new root cause, it adds the axes that cause suggests and runs another pass. Its result file holds the axis list, the result for each axis (pass, or fail with its root cause, reproduction command, and output), and the stop reason. When every variant fails, the file says at the top that the root cause must be fixed rather than the variants patched one by one.
   2. **Synthesis.** One node merges the result files into one required-changes list, grouped by class and root cause, that carries every failed variant. When the verdict reports only one or two required changes, skip this node: the sweep nodes still run, and their result files go straight to the fix node. A failed variant at a sibling location of the same class is a companion item when it passes guards (a)-(c) of `SKILL.md`, The purpose boundary. The synthesized list marks it as a companion item, and the lead adds it to the task's plan, the plan under review, as a new COMPANION row under guard (d): `COMPANION: <variant> <- <request IS row> : <why expected>`. The lead amends the plan in place, notes when and why the row was added, and never rewrites earlier rows. When synthesis is skipped, the lead marks the companion items from the result files. A variant that fails a guard isn't a companion item: the list marks it as a follow-up, it goes to the follow-up file (`SKILL.md`, Follow-up record) with the guard it fails, and the fix leaves it out.
   3. **Fix.** The fix nodes fix each class as a class, at its root cause, covering every failed variant in the list or result files other than those step 2.2 recorded as follow-ups, and use those variants to confirm the cause is gone. For code that handles input, the fix delivers three defaults: a boundary that doesn't crash, so an unexpected exception in one rule or check becomes a parseable result for that rule and the overall report still completes; one shared helper in place of checks that were duplicated; and one seeded, deterministic boundary or mutation test, with no sleeps, that feeds mutated valid inputs to the real entry point and asserts a parseable result every time. That test is a `guard` row, added to the plan's risk list when it lacks one (`references/execution.md`, Regression tests). For a class that isn't input handling, these defaults don't apply, and the fix node's report says so. Independent fixes run in parallel.
3. Rerun the QA that the fixes affect, using the reuse rule above for the rest.
4. End with an ultrabrain delta re-review by a new reviewer, never the one that returned REVISE, unless the Evidence gate below applies. Pass the delta diff, the required changes the previous verdict cited, the sweep result files with their axis lists, the synthesized required-changes list when synthesis ran, and fresh evidence for the affected targets. The reviewer checks that every failed variant is fixed or, when step 2.2 recorded it as a follow-up, that the record names a guard of (a)-(c) that the variant actually fails, and that each class test fails with the fix reverted and passes with it, with a capture of both, including for each interleaving or input the previous verdict named. It reads each axis list and judges whether a direction is missing; a missing axis is goal failure, so it is a required change and returns REVISE. Its scope isn't limited to those files: it reviews the delta in full, and reports every defect it finds in one verdict as in Final ultrabrain review. Any new defect or variant that shows goal failure, an introduced regression, or invalid evidence is a required change and returns REVISE; anything else it raises is a follow-up note. Don't paste an old approval onto changed code, and don't run a fresh whole-project review each round.

**Evidence gate.** When every required change a verdict lists is `layer: EVIDENCE` and the task's files haven't changed since the reviewed commit, steps 2 to 4 above don't run: no variant sweep, no synthesis, and no new ultrabrain reviewer. One evidence node fixes the named records under `SKILL.md` rule 4 and reruns each finding's reproduction into a new capture. Then one confirmation node, on a cheaper category than the reviewer's, reads the lint output and those captures and judges only whether the named evidence defects are gone, writing `VERDICT: PASS` or `VERDICT: FAIL`; it never judges product behavior. On PASS the round closes, and that PASS counts as the review's APPROVED for `SKILL.md` rule 6 and Merge and finish. On FAIL the evidence fix retries under `references/execution.md`, Recovery. A verdict with any `layer: PRODUCT` item, or any change to the task's files, follows the steps above unchanged.

Repeat until APPROVED. There is no round limit; see the owner policy in `SKILL.md`, Native skills and mode.

## Merge and finish

- Follow `SKILL.md` rule 6 and Task shape for approved merges.
- If integrating with other merges changes a task's behavior, rerun only the affected targets. If the approved implementation changes substantively, get an ultrabrain re-review by a new reviewer before merging.
- After all tasks merge, right before the final report, run the full verification set once on the merged result: every QA scenario plus the repository's test suite, typecheck, and build where it has them. Until that point the per-target reuse rule decides what reruns; this one full pass is the only exception. Refill the conformance table from this pass for the report. Record loop evidence and the final checkpoint from this final pass so the loop's tree-hash rule is satisfied. For a failing target, follow `SKILL.md`, Task shape, for post-merge continuation.
- When the goal is satisfied, perform the cleanup in `SKILL.md`, Finish, complete the loop goal, and deliver the report below.

## Final report checklist

- Results: what was delivered and merged.
- Evidence: the QA scenarios and tests, with artifact locations.
- Conformance: the conformance table refilled from the final full pass, and the COMPANION items delivered.
- Limits: what wasn't proven or what the host couldn't do.
- Removed tests: each existing or approved test removed, why, and the evidence that replaces it (`references/execution.md`, Regression tests), or none.
- Separate findings: follow `SKILL.md`, Follow-up record; give each follow-up the companion guard (a)-(d) it fails, so its exclusion is judgeable.
