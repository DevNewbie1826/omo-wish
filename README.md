# omo-wish

`/wish`: 소원을 빕니다.

[OmO](https://github.com/code-yeongyu/oh-my-openagent) 플러그인입니다. 슬래시 명령 하나로 `wish` 스킬을 불러와, 요청한 목적 하나를 기준으로 계획, TDD, QA, 리뷰를 끝까지 진행합니다. 예전처럼 긴 프롬프트를 통째로 보내고 범용 ultrawork 모드를 자동으로 켜는 방식이 아닙니다. 필요한 단계에서 필요한 지침만 읽는 스킬 방식입니다.

## 설치

```sh
omo install https://github.com/DevNewbie1826/omo-wish
```

프로젝트에만 설치하려면 `-l`을 붙이세요:

```sh
omo install -l https://github.com/DevNewbie1826/omo-wish
```

로컬 개발용(복사 없이 현재 폴더를 직접 로드):

```sh
omo install /path/to/omo-wish
```

제거:

```sh
omo remove https://github.com/DevNewbie1826/omo-wish
```

설치 후 새 세션(또는 `/reload`)부터 반영됩니다.

## 호환성

아래 환경에서 실제로 테스트했습니다.

| 구성 요소 | 테스트한 버전 |
| --- | --- |
| omo | 5.1.2 |
| Senpi | 2026.9.29-3 |
| Bun | 1.4 |

이건 테스트한 조합일 뿐, 최소 지원 버전이 아닙니다. 더 오래된 버전에서 동작하는지는 확인하지 않았습니다. 플러그인은 `pi.skills` 매니페스트 항목과 확장의 `before_agent_start` 이벤트를 지원하는 호스트를 전제로 합니다.

## 사용법

입력창에 `/`를 치면 목록에 **wish: 소원을 빕니다** 가 뜹니다.

```
/wish <작업 설명>
```

예:

```
/wish 로그인 리다이렉트 버그 수정
```

- 인자는 템플릿 맨 앞의 `$ARGUMENTS` 자리에 그대로 들어갑니다. 인자 안에 `$ARGUMENTS`나 `$1` 같은 글자가 있어도 다시 치환하지 않고 문자 그대로 전달합니다.
- 인자 없이 `/wish`만 입력해도 됩니다. 이때는 대화 맥락에서 원하는 결과를 파악합니다.
- `/wishful`, `/WISH` 같은 다른 명령이나, 평범한 문장 속 `ulw` 같은 단어로는 wish 스킬이 켜지지 않습니다. (호스트 모드에 대한 설명은 아래 모드 동작을 보세요.)

## 동작 흐름

`/wish`를 실행하면 이런 순서로 진행됩니다.

```
/wish <요청>
  │
  ├─ prompts/wish.md 확장: 인자 + "wish 스킬을 읽어라" 지시 + 예약 마커
  │
  ├─ extensions/wish.js: 끝에 붙은 마커를 보고 설치된
  │   skills/wish/SKILL.md 절대 경로를 숨은 메시지로 알려줌
  │
  └─ 에이전트가 SKILL.md(핵심 규칙)를 읽고, 단계마다
      references/ 파일을 하나씩 추가로 읽음
        planning.md      → 발견, 목표, 계획
        execution.md     → worktree, DAG, TDD 실행
        verification.md  → QA, PR, 최종 리뷰, REVISE
```

### 1. 진입점과 예약 마커

`prompts/wish.md`는 짧은 템플릿입니다. 끝에 한 줄짜리 `<!-- omo-wish:entry:v1 -->` 마커가 붙습니다. `extensions/wish.js`는 확장된 프롬프트 끝에서 이 마커를 찾으면, 플러그인 안의 `skills/wish/SKILL.md` 절대 경로를 `omo-wish:skill` 숨은 메시지로 전달합니다. 설치 경로에 공백, 따옴표, `#`, 한글 같은 문자가 있어도 JSON 이스케이프로 안전하게 넘깁니다. 확장은 상태를 저장하지 않습니다. 세션 상태나 전역 플래그도 건드리지 않습니다.

마커는 **예약된 활성화 문법**일 뿐, 인증 수단이 아닙니다. 누가 마커 전체를 직접 붙여 넣으면 의도적으로 활성화한 것으로 간주합니다. 명령을 누가 쳤는지 위조 불가능하게 증명하는 장치는 없습니다.

템플릿 자체에도 "사용 가능한 `wish` 스킬을 읽어라"라는 지시가 들어 있습니다. 그래서 큐에 쌓인 입력처럼 확장 훅이 건너뛰어지는 경로에서도 에이전트가 스킬을 찾아갈 수 있습니다. 이 경로는 코드를 따라가며 확인한 것이고, 실제 스트리밍 세션을 끝까지 돌려 본 라이브 테스트는 아닙니다.

### 2. 단계별 스킬 로딩

핵심 파일 `skills/wish/SKILL.md`에는 전체를 지배하는 규칙과, 어느 시점에 어떤 참조 파일을 읽을지만 들어 있습니다. 세부 지침은 `references/`의 세 파일에 나뉘어 있고 해당 단계에 들어갈 때만 읽습니다. 처음부터 긴 지침을 전부 떠안지 않으니, 서로 충돌하는 정책이 한꺼번에 켜지는 일이 줄어듭니다.

### 3. 원래 목적이 경계

요청한 목적 하나가 발견, 계획, TDD, QA, 리뷰 전부의 범위를 정합니다.

- 영향 범위를 넓게 조사하더라도, 영향받는 모든 사람의 불편을 다 해결하라는 뜻은 아닙니다.
- 요청 범위 안에서 빠진 부분이나 새로 생긴 회귀는 묻지 않고 알아서 고칩니다.
- 관련 없는 버그나 개선점은 고치지 않습니다. 대신 증거, 재현 방법, 영향, 제외한 이유를 적어 나중 작업으로 남깁니다.
- 이미 승인한 단계를 다시 승인받지 않습니다.

### 4. 계획과 실행

- 맥락·이력을 조사하고 영향받는 대상을 파악한 뒤, 요청 범위 안의 이상 상태·차이·사용자 관점 QA를 정의합니다. 이를 ulw-plan 절차로 검토해 실행 DAG의 시드 계획을 완성하고, 그 계획을 ulw-loop 목표로 등록합니다. 루프 안에서 mass-ulw로 DAG를 구성해 실행합니다.
- ulw loop 목표는 하나만 만듭니다. 요청한 작업은 그 안의 태스크 하나이고, 현재와 목표 상태의 차이는 그 태스크 DAG의 노드가 됩니다.
- 태스크 하나는 worktree 하나, PR 하나, DAG 하나입니다. 목적이 다른 독립 태스크는 동시에 돌리고, 의존 태스크는 선행 태스크가 merge된 뒤 시작합니다. 승인된 merge는 한 번에 하나씩 합니다.
- 새 런타임 동작은 기존 테스트를 먼저 확인한 뒤, 필요한 동작에 대해 실패(RED), 최소 구현으로 통과(GREEN), 동작을 유지한 개선(REFACTOR)을 진행합니다. 충분한 기존 테스트는 활용하고, 요구사항이 아닌 내부 호출이나 조정 가능한 값을 고정하지 않습니다. 문구를 고정하는 테스트나 마크다운에 대한 가짜 RED는 쓰지 않습니다.

### 5. 검증, PR, 최종 리뷰

순서는 합산 QA, PR 생성, ultrabrain 최종 리뷰입니다. 리뷰 결과는 APPROVED 또는 REVISE입니다. 완료·승인을 막을 수 있는 건 목표 미달, 새로 생긴 회귀, 잘못된 증거뿐입니다. 관련 없는 품질 지적은 나중 작업 메모로 남습니다.

REVISE가 나오면 같은 worktree와 같은 PR에서 수정용 DAG를 새로 만들고, 영향받은 QA만 다시 돌린 뒤 바뀐 부분만 다시 리뷰받습니다. 매번 전체 프로젝트를 새로 리뷰하지 않습니다.

### 6. 증거 재사용

이전 증거는 입력, 의존성, 환경이 바뀌지 않았는지 확인한 뒤에만 재사용합니다. 처음 수집한 출처는 그대로 남기고, 왜 아직 유효한지 적습니다. 영향을 받았거나 확실하지 않은 부분은 다시 돌립니다. 바뀐 코드에 예전 승인을 그대로 붙여 넣는 건 재리뷰가 아닙니다.

## 모드 동작

- 이제 `/wish`는 범용 ultrawork 모드를 **자동으로 켜지 않습니다**. 예전 버전의 `extensions/wish-ultrawork-arm.js`는 제거됐습니다.
- 사용자가 이미 켜 둔 ultrawork 같은 모드는 **그대로 둡니다**. 끄거나 초기화하지 않습니다. 켜 둔 모드가 없어도 그대로 동작합니다.
- 다만 호스트가 원시 입력의 키워드로 모드를 켜는 기본 동작은 그대로 남아 있습니다. 예를 들어 `/wish` 인자에 `ulw`나 `ultrawork`를 직접 쓰면, 템플릿이 확장되기 전에 호스트가 그 모드를 켤 수 있습니다. 이 플러그인은 그렇게 켜진 모드를 막거나 바꾸지 않습니다. 그러니 `/wish`로는 어떤 경우에도 범용 모드가 켜지지 않는다고 기대하지는 마세요. 플러그인 스스로 켜지 않을 뿐입니다.

## 네이티브 plan 게이트 호환성

`/wish`를 쓴다고 호스트의 네이티브 plan-reviewer 게이트가 자동으로 열리지는 않습니다. 그 게이트는 사용자가 ulw-plan 흐름을 명시적으로 요청했을 때처럼 호스트 조건이 맞을 때만 열립니다.

- 게이트가 정말로 열려 있으면 네이티브 plan-reviewer로 계획을 리뷰합니다.
- 닫혀 있으면 이름을 명시한 카테고리 기반 읽기 전용 리뷰어로 대신 계획을 리뷰합니다. 호스트의 호환성 표가 허용하는 방식입니다.
- 게이트를 수동으로 풀거나, 거부된 호출을 반복해서 재시도하지 않습니다.

## 구조

```
omo-wish/
├── package.json                  # pi manifest: pi.prompts, pi.extensions, pi.skills
├── prompts/
│   └── wish.md                   # 슬래시 명령 템플릿 (description = 메뉴 설명)
├── extensions/
│   └── wish.js                   # 마커를 보고 스킬 경로를 알려주는 확장
├── skills/
│   └── wish/
│       ├── SKILL.md              # 핵심 규칙과 단계별 로딩 지점
│       └── references/
│           ├── planning.md
│           ├── execution.md
│           └── verification.md
├── test/
│   └── wish.test.js              # 동작 테스트
└── scripts/
    └── verify.mjs                # 실제 호스트 로더로 확인하는 검증 스크립트
```

`package.json`의 `pi.skills: ["skills/wish"]`로 스킬이 호스트에 등록됩니다.

## 개발과 검증

```sh
bun test
bun scripts/verify.mjs .
```

`scripts/verify.mjs`는 설치된 Senpi의 실제 로더(프롬프트 템플릿, 스킬, 확장 러너)로 패키지를 불러와 확인합니다. 테스트와 검증기의 기본 Senpi 위치는 현재 사용자 홈 아래 `.bun/install/global/node_modules/@code-yeongyu/senpi`입니다. 다른 위치에 설치했다면 `SENPI_ROOT` 환경 변수로 설치 경로를 지정하세요.

## 커스터마이징

- 메뉴 설명과 진입 템플릿은 `prompts/wish.md`에 있습니다. 끝의 마커 줄은 지우지 마세요. 지우면 확장이 스킬 경로를 전달하지 않습니다.
- 작업 규칙은 `skills/wish/SKILL.md`와 `references/` 파일에서 고칩니다.
