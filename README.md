# omo-wish

`/wish`: 소원을 빕니다.

[OmO](https://github.com/code-yeongyu/oh-my-openagent) 플러그인입니다. 슬래시 명령 하나로 `wish` 스킬을 불러와, 요청한 목적 하나를 기준으로 계획, 회귀 테스트, QA, 리뷰를 끝까지 진행합니다. `/wish`를 입력하면 ultrawork 모드도 켜지고, 그 위에서 wish 스킬이 이번 요청의 범위와 절차를 정합니다. 긴 프롬프트를 통째로 보내지 않고, 필요한 단계에서 필요한 지침만 읽습니다.

## 설치

```sh
omo install https://github.com/DevNewbie1826/omo-wish
```

프로젝트에만 설치하려면 `-l`을 붙이세요:

```sh
omo install -l https://github.com/DevNewbie1826/omo-wish
```

로컬 개발용(복사 없이 현재 폴더를 직접 로드):

```sh
omo install /path/to/omo-wish
```

제거:

```sh
omo remove https://github.com/DevNewbie1826/omo-wish
```

설치 후 새 세션(또는 `/reload`)부터 반영됩니다.

## 호환성

아래 환경에서 실제로 테스트했습니다.

| 구성 요소 | 테스트한 버전 |
| --- | --- |
| omo | 5.1.17 |
| Senpi | 2026.10.8 |
| Bun | 1.4.2 |

이건 테스트한 조합일 뿐, 최소 지원 버전이 아닙니다. 더 오래된 버전에서 동작하는지는 확인하지 않았습니다. 플러그인은 `pi.skills` 매니페스트 항목과 확장의 `before_agent_start` 이벤트를 지원하는 호스트를 전제로 합니다.

## 사용법

입력창에 `/`를 치면 목록에 **wish: 소원을 빕니다** 가 뜹니다.

```
/wish <작업 설명>
```

예:

```
/wish 로그인 리다이렉트 버그 수정
```

- 인자는 템플릿 맨 앞의 `$ARGUMENTS` 자리에 그대로 들어갑니다. 인자 안에 `$ARGUMENTS`나 `$1` 같은 글자가 있어도 다시 치환하지 않고 문자 그대로 전달합니다.
- 인자 없이 `/wish`만 입력해도 됩니다. 이때는 대화 맥락에서 원하는 결과를 파악합니다.
- `/wishful`, `/WISH` 같은 다른 명령은 wish 스킬을 부르지 않습니다. 평범한 요청에 `ulw`나 `ultrawork`를 쓰면 일반 ultrawork 모드는 켜질 수 있지만, wish 스킬이 선택되지는 않습니다. (자세한 건 아래 모드 동작을 보세요.)

## 동작 흐름

`/wish`를 실행하면 이런 순서로 진행됩니다.

```
/wish <요청>
  │
  ├─ prompts/wish.md 확장: 인자 + "Use ultrawork. Read and follow the `wish` skill"
  │
  ├─ extensions/wish.js: 확장된 문장의 ultrawork 키워드를 보고
  │   아직 꺼져 있으면 호스트 ultrawork 모드를 한 번 켬
  │
  ├─ 호스트가 등록된 스킬 목록(pi.skills)에서 wish를 찾아 경로를 제공
  │
  └─ 에이전트가 SKILL.md(핵심 규칙)를 읽고, 단계마다
      references/ 파일을 하나씩 추가로 읽음
        planning.md      → 발견, 이상 상태, 계획, architect 계획 리뷰 (+ ulw-plan 스킬)
        execution.md     → 루프 목표, worktree, DAG, 회귀 테스트 (+ ulw-loop, mass-ulw 스킬)
        verification.md  → QA, PR, 최종 리뷰, REVISE, merge
```

### 1. 진입점

`prompts/wish.md`는 짧은 템플릿입니다. 맨 앞의 `$ARGUMENTS` 뒤에 ``Use ultrawork. Read and follow the `wish` skill for this request.`` 한 줄만 붙고, 작업 규칙은 하나도 담지 않습니다. 스킬 경로는 `pi.skills` 등록으로 호스트가 제공합니다.

`extensions/wish.js`는 확장된 문장에서 `ultrawork`나 `ulw`를 단어 단위로(대소문자 구분 없이) 찾습니다. 호스트 연동이 가능하고 아직 켜지지 않은 세션의 실제 호출이면 호스트의 `markArmed(sessionId)`로 활성화를 기록하고, 호스트 지시문만 `omo-ultrawork:directive` 숨은 메시지로 넘깁니다. wish 전용 지시는 덧붙이지 않습니다. 이미 켜져 있거나, 키워드가 없거나, 미리보기이거나, 호스트 연동이 없으면 아무 메시지도 보내지 않고 상태도 바꾸지 않습니다. 별도의 활성화 상태를 만들지 않고 호스트가 제공하는 세션 상태를 사용합니다.

이 키워드 처리는 일반 ultrawork 활성화일 뿐입니다. 평범한 `ulw` 요청을 wish로 보내지 않습니다. 어떤 스킬을 쓸지는 프롬프트 내용과 등록된 스킬 목록을 보고 에이전트가 고릅니다.

템플릿 자체에 "`wish` 스킬을 읽고 따르라"는 지시가 들어 있습니다. 그래서 큐에 쌓인 입력처럼 확장 훅이 건너뛰어지는 경로에서도 에이전트가 스킬을 찾아갈 수 있습니다. 이 경로는 코드를 따라가며 확인한 것이고, 실제 스트리밍 세션을 끝까지 돌려 본 라이브 테스트는 아닙니다.

### 2. 단계별 스킬 로딩

`skills/wish/SKILL.md`가 전체를 지배하는 계약입니다. 세 참조 파일은 단계마다 네이티브 스킬(`ulw-plan`, `ulw-loop`, `mass-ulw`)을 wish에 맞게 구체화하고, 해당 단계에 들어갈 때만 읽습니다. 처음부터 긴 지침을 전부 떠안지 않으니, 서로 충돌하는 정책이 한꺼번에 켜지는 일이 줄어듭니다.

| 단계 | 들어갈 때 꼭 읽는 파일 |
| --- | --- |
| 1. 발견과 계획 | `references/planning.md`, `ulw-plan` 스킬 |
| 2. 실행 (단일 architect 계획 리뷰 통과 후) | `references/execution.md`, 목표를 만들기 전에 `ulw-loop` 스킬, DAG를 정의하기 전에 `mass-ulw` 스킬과 그 `references/planning.md` 전체, 이어서 `references/verification.md` |
| 3. 검증, PR, 리뷰 | 새로 읽을 파일 없음. 2단계에서 `references/verification.md`를 보고 정의해 둔 DAG의 마무리 노드가 프로덕션 노드 뒤에 실행됩니다 |

REVISE가 나오면 처음부터 다시 시작하지 않고 2단계로 돌아갔다가 3단계로 돌아옵니다. 읽기 규칙(이번 실행에서 직접 열 것, 없는 네이티브 스킬은 차단 사항으로 보고, 단계 첫 보고에 읽은 파일 적기)은 SKILL.md에 있습니다.

단계마다 스킬 이름을 직접 적는 데는 이유가 있습니다. omo의 키워드 스킬 포인터는 사용자가 직접 입력한 원문만 봅니다. 템플릿이나 스킬 본문에 스킬 이름이 들어 있어도 그 스킬이 자동으로 붙지 않습니다. 그래서 wish가 단계별로 읽을 스킬을 이름으로 지정합니다.

## 스킬이 정하는 것

여기는 개요입니다. 규칙의 정확한 문장은 각 항목이 가리키는 스킬 파일에만 있고, README와 다르게 읽히면 스킬 파일이 맞습니다.

### 발견과 계획

1단계 규칙은 `references/planning.md`에 있습니다.

- 발견은 시작부터 `explore`와 `librarian`을 백그라운드에서 병렬로 띄워 최대한 모으고, 모든 열린 질문이 풀리거나 두 번 연속 새 사실이 없으면 멈춥니다.
- 경계를 정하기 전에 결과가 닿는 모든 상대(코드·프로그램, 다른 개발자, 최종 사용자)를 네 단계로 명시합니다: 누가 닿는지, 지금 어떻게 쓰는지, 바뀐 뒤 어떻게 쓰는지, 어디서 걸리는지.
- 이상 상태는 표로 두고, 행마다 그 상대가 보기에 걸리거나 이상하거나 퇴보하거나 나빠지는 게 없는 속성으로 적으며 이유를 붙입니다.
- 성공 기준을 쓰기 전에 변경이 닿는 행동마다 성격을 나눕니다. 요청이 바꾸는 행동(버그 수정, 복원, 새 코드)은 의도(명세·요구)와 대조합니다. 그대로 남아야 하는 행동은 저장된 상태와 부작용(예약 작업, 큐, 저장된 레코드)까지 포함해, 변경 전에 기록한 지금의 실제 값과 대조합니다. 틀려 보여도 그 값이 기준이고, 내 생각의 정답으로 바꾸지 않습니다. 이 기록은 먼저 쓰는 테스트가 아니라 관찰입니다. 기준은 정확한 단언 줄이 아니라 관찰 가능한 행동을 가리킵니다. 같은 흐름의 앞선 단언이 먼저 터지면 그 기준은 충족될 수 없기 때문입니다.
- 모든 이상 상태 행에는 GAP 행이나 이미 충족됨을 보이는 `no gap` 증거가 붙습니다. GAP 행의 열은 현재 상태 | 사용자 영향(필수) | 원인(알면)입니다.
- 계획의 todo마다 닫는 GAP, 방법, 그 방법을 고른 이유, 체크박스, DAG 필드(쓰는 파일, 선행 조건)를 적습니다.
- QA는 실제 표면, 정확한 호출, 하나의 PASS/FAIL 관찰값, 성공·실패 경우, 증거 경로를 적고, 이상 상태 행마다 최소 하나와 그 이유를 둡니다. 시나리오는 실제로 수행한 단계만 증명합니다. 주장하는 단계(재연결, 복원 등)를 건너뛰거나 흉내만 낸 리허설은 그 단계의 증거가 아니며, 산출물은 그 단계 뒤의 상태를 보여야 합니다.
- 계획 리뷰는 `architect` 카테고리 한 라운드뿐입니다. 지적된 차단 사항은 고치고 계획의 "Plan review record"에 기록하며 다시 리뷰하지 않습니다. 다만 실행에 들어가기 전에 리드가 계획을 한 번 다시 읽고 기록한 수정이 실제로 계획에 들어갔는지 확인합니다. 이 확인은 두 번째 리뷰 라운드가 아닙니다. `architect`가 호스트 목록에 없으면 멈추고 차단 사항으로 보고합니다.

### 반드시 지키는 규칙

요청 크기나 모델과 상관없이 늘 지킵니다. SKILL.md의 "Non-negotiable rules"가 원본입니다.

- 단계마다 필요한 파일을 그 단계에 들어갈 때 직접 읽고, 첫 보고에 읽은 파일을 적습니다.
- 목표는 ulw-loop SDK로만 만들고, 그 결과로 받은 handoff를 `create_goal`로 등록합니다.
- 태스크 파일을 바꾸는 일(테스트 작성, REVISE 수정 포함)은 모두 mass-ulw로 정의한 DAG 노드가 태스크의 worktree에서 합니다. 리드는 아무리 작은 수정이라도 직접 고치지 않습니다.
- mass-ulw의 `references/planning.md`를 다 읽기 전에는 DAG를 정의하지 않습니다.
- 합산 검증 전에는 PR을 열지 않고, ultrabrain 리뷰의 APPROVED 전에는 merge하지 않습니다.

### 원래 목적이 경계

요청한 목적 하나와 그에 딸린 companion 항목이 발견, 계획, 테스트, QA, 리뷰 전부의 범위를 정합니다. 넓게 조사하는 건 영향 범위를 찾기 위해서이고, 영향받는 모든 불편을 고치라는 뜻은 아닙니다. 범위 안은 요청의 이상 상태 행과 COMPANION 행입니다. 계획에 넣은 COMPANION 행을 전달하지 못하면 요청 미달과 같습니다.

companion은 이번 변경과 같은 결이고, 요청자가 "왜 이건 같이 안 했지?"라고 PR에서 물을 만한 항목입니다. companion은 네 가드를 모두 통과해야 합니다: (a) 한 홉만 - 요청의 이상 상태 행에 바로 붙이고 companion의 companion은 두지 않습니다. (b) 새 소유자 결정 없음 - 사용자가 골라야 하는 일은 companion이 아니라 질문이나 후속 기록입니다. (c) 같은 태스크와 PR - 별도 태스크가 필요한 일은 companion이 아닙니다. (d) 눈에 보임 - 계획에 `COMPANION: <항목> <- <요청 IS 행> : <왜 예상되는지>` 행으로 적습니다. 고치는 김에 같은 패턴으로 발견한 형제 위치의 기존 버그도 companion입니다.

요청이 전달되지 않았거나, 이번 변경이 회귀를 만들었거나, 증거가 잘못됐다면 범위 안이니 같은 태스크에서 알아서 고칩니다. 나머지는 이미 있던 진짜 버그라도 고치지 않고 후속 기록으로 남깁니다.

### 후속 기록

범위 밖 발견 사항은 루프 증거 디렉터리의 `follow-ups.md` 한 파일에 내용, 재현, 증거, 영향, 제외 이유를 적습니다. 제외 이유에는 왜 companion이 아닌지, 어느 가드 (a)-(d)를 어기는지도 적습니다. 영구 메모리에는 짧은 요약, 이번 작업에서 고치지 않은 이유, 파일 경로를 색인으로 남기고, 최종 보고에도 빠짐없이 적습니다. 없으면 없다고 쓰고 빈 파일은 만들지 않습니다. 경로를 정하는 방법과 루프가 생기기 전의 처리는 SKILL.md의 "Follow-up record"에 있습니다.

### 태스크와 런

- 목적 하나가 태스크 하나입니다. merge 전 전달 단위마다 태스크 하나는 worktree 하나, PR 하나, 브랜치 하나를 씁니다. 현재와 이상 상태의 차이는 태스크가 아니라 DAG 노드가 됩니다.
- 태스크의 작업은 순차적인 런으로 진행됩니다. 런 하나는 mass-ulw `workflow` DAG 하나(mass-ulw 단계 하나)입니다. 첫 런 뒤에 앞 런이 증명한 것을 바탕으로 다듬기, REVISE 수정, merge 후 수정 런을 이어 갑니다. merge 전의 다듬기·REVISE 수정 런은 같은 worktree와 같은 PR에서 돌고, merge 후 수정은 같은 목적의 연장으로 병합된 main에서 새 worktree와 새 PR을 만들어 ultrabrain 리뷰까지 거칩니다. 속도를 위해 런을 병렬로 쪼개지 않고, 동시성은 런 안의 병렬 노드에서 나옵니다.
- 목적이 다른 일만 별도 태스크가 됩니다. 독립 태스크는 동시에 돌고, 의존 태스크는 선행 태스크가 merge된 뒤 시작합니다.
- DAG 노드는 작게 나누고 카테고리는 크기가 아니라 난이도로 고릅니다. 스킬은 작업 노드에 쓸 카테고리 이름을 정해 주지 않고, 호스트의 `task` 도구가 사용 가능하다고 나열한 것만 씁니다. 네이티브 스킬 표에 나오는 이름이라도 이 호스트에 없으면 쓰지 않습니다. 리뷰 카테고리 `architect`와 `ultrabrain`은 예외로 이름이 정해져 있습니다. 자세한 노드 설계는 `references/execution.md`에 있습니다.
- 구현 노드가 병렬로 도는 배치마다 검증 노드를 하나 둡니다. 검증 노드는 계획의 고정 기준 SHA에서 각 노드의 결과를 diff하고, 각 노드의 VERIFY를 다시 돌리고, 결과를 성공 기준과 대조합니다. 그 난이도는 배치에서 가장 어려운 노드 이상입니다. 다음 배치는 `dependsOn`만이 아니라 그 검증 노드의 판정 파일로 기다립니다: 판정 파일은 `<evidenceRoot>/<run-key>/<node-id>-verdict.md`이고 첫 줄이 정확히 `VERDICT: PASS` 또는 `VERDICT: FAIL`입니다. 이 게이트는 이행적이라, 어떤 검증 노드의 하류 노드는 첫 필수 단계로 상류 판정 파일을 모두 읽고 하나라도 PASS가 아니면 `BLOCKED: <id> not PASS`로 멈춥니다. `BLOCKED`로 멈춘 노드는 상류 판정이 바뀌기를 기다리지 않고, 그 `BLOCKED` 줄을 마지막 답으로 남기고 바로 끝냅니다. 모니터·알람·폴링을 걸지 않으며, 노드의 첫 필수 단계에 이 점을 분명히 적습니다. 막힌 일을 다시 맡길지, 언제 맡길지는 판정을 본 리드가 `amend`나 수정 런으로 정합니다. 스스로 다시 움직인 노드는 리드의 배정 밖에서 일하게 되어, 리드가 이미 새로 맡긴 일을 커밋할 수 있습니다.

### 회귀 테스트

세 원칙을 먼저 둡니다: (1) 코드 먼저 - 테스트는 그다음입니다. (2) 동작하면 테스트를 더합니다 - 중요한 건 마지막에 테스트가 있다는 것이지 쓰는 순서가 아닙니다. (3) 겉으로 보이는 행동만 테스트하고 내부는 테스트하지 않습니다 - 테스트는 행동이 바뀔 때만 깨집니다. RED를 먼저 쓰라는 규칙은 없습니다.

- 계획에는 바뀌는 행동마다 위험 목록 한 줄을 적습니다. `guard` 줄에는 사용자가 겪을 회귀와 그 회귀를 맡을 노드를 적고, 이미 막는 테스트가 있으면 그 테스트도 적습니다. `no-test` 줄에는 정해진 사유만 씁니다. 문서·프롬프트 변경이거나, 이 저장소에서 테스트할 수 없어 QA 시나리오로 대신하는 경우입니다. 재시작·복구 같은 행동에 대한 주장에 기대는 `no-test` 줄은 그 주장을 세우는 출처를 적고, 검증은 그 출처가 주장을 실제로 세우는지 대조해 파일과 줄을 증거로 남깁니다. 출처가 없거나 출처가 세우지 못하는 주장은 잘못된 증거입니다. 새 테스트는 `guard` 줄에만 씁니다.
- 노드는 구현이 실제 표면에서 동작하는지 확인하고, guard마다 행동·계약에 붙은 테스트를 하나 둡니다. 코드 먼저, 테스트는 그다음입니다. 버그 수정은 고치기 전에 버그부터 재현합니다. 이미 그 회귀를 막는 기존 테스트가 있으면 이름만 적고 새 테스트는 두지 않지만, 그 테스트에도 주입 검사는 똑같이 합니다.
- guard 테스트마다 회귀 주입 검사를 합니다. guard가 말하는 회귀를 일부러 만들어 테스트가 실패하는지 보고, 원복해서 다시 통과하는지 봅니다. 버그 수정은 수정만 되돌리고, 새 코드는 그 회귀를 만드는 가장 작은 고장 하나를 넣습니다. 증거는 주입 diff, 실패 출력, 원복 후 통과 출력입니다. 주입해도 통과하는 테스트는 증거가 아닙니다. 녹색 종료만으로는 아무것도 증명하지 않습니다. 주입 실행, 원복 후 실행, 합산 검증 실행 모두 실행된 테스트 수가 0보다 크고 실행된 테스트 중에 그 테스트의 이름이 보여야 하며, 주입 실행은 그 회귀를 검사하는 단언에서 실패해야 합니다. `-t`/`-run` 필터의 이스케이프되지 않은 정규식은 그 테스트나 모든 테스트를 건너뛸 수 있고, `go test -run` 같은 일부 러너는 그래도 0으로 끝납니다.
- guard 테스트는 guard가 의도한 결과를 단언합니다. 그 결과의 반대를 요구하는 녹색 테스트(예: 빠져나간 자식 프로세스가 살아 있어야 통과)는 증거가 아닙니다.
- 동시성, 순서, 구독 정체성을 바꾸는 노드에서는 영향받는 인터리빙마다 `guard` 줄이 되고(위험 목록에 없으면 추가), 같은 커밋에 그 인터리빙을 결정적으로(타이밍이 아니라 장벽·명시적 해제로) 재현하는 guard 테스트를 넣습니다. 최소 세 경우: 동시 두 요청, 같은 ID 재구독, 새 상태 뒤에 도착하는 늦은 실패·오래된 결과. 수정을 되돌리거나 회귀를 주입하면 그 인터리빙에서 실패해야 하고, 보호 분기를 통째로 지우는 굵은 주입에서만 실패하는 테스트는 부족합니다.
- debugging 스킬은 원인이 확정되지 않은 버그이거나, 주입해도 테스트가 통과하는데 이유를 모를 때만 씁니다.
- 프로덕션 변경과 그 증거는 같은 노드에 둡니다.
- 기존·승인된 테스트는 지우거나 약화하거나 건너뛰지 않고, 통과시키려고 단언을 느슨하게 하지 않습니다. 그래도 지우면(구현 세부를 고정해 버리는 테스트를 버리는 경우 포함) 노드 보고, PR 본문, 최종 보고에 지운 테스트, 이유, 대체 증거를 적습니다.
- 계획 리뷰는 위험 목록을 검토합니다. 사용자가 겪을 회귀에 `guard`나 유효한 `no-test` 줄이 없거나, `no-test` 사유가 정해진 것이 아니면 막습니다. 노드가 끝날 때의 리드 확인, 합산 검증, ultrabrain 리뷰는 guard마다 테스트와 주입 증거가 있는지 대조하고, 빠진 증거는 잘못된 증거로 봅니다. 목록에 없던 행동이 나중에 발견되면, 요청 미달이나 새 회귀를 보여주거나 companion 가드 (a)-(c)를 통과하면 범위 안이니 같은 worktree에서 고치고, 그 밖이면 후속 기록으로 남깁니다.

세부 규칙은 `references/execution.md`의 "Regression tests"에 있습니다.

### 검증, PR, 리뷰

순서는 합산 검증, PR 생성, ultrabrain 최종 리뷰입니다. 합산 검증은 먼저 계획의 이상 상태 행마다 적합성 표(conformance table)를 만듭니다: 이상 상태 행, 닫은 GAP 또는 이미 충족됨 증거, 닫은 todo, PASS/FAIL이 붙은 QA 증거 경로, 지키는 guard 행. 증거가 빠지거나 실패한 행은 불일치라 같은 worktree에서 고친 뒤 표를 다시 채우고, 모든 행이 맞을 때만 PR을 엽니다. 합산 검증과 ultrabrain 리뷰는 계획의 위험 목록과 그 증거도 대조합니다(위 회귀 테스트). 레코드는 개수만이 아니라 식별자와 표식으로 비교합니다. 합계는 그대로인데 레코드가 바뀌거나 사라질 수 있고, 합계까지 잡는 locator는 합계를 검사하게 됩니다. QA 비교기·하네스는 손상되거나 빠진 입력에서 반드시 실패해야 하고, 그 대조군 실패를 통과 실행 옆에 캡처합니다. 통과만 보인 비교기는 증거가 아닙니다. 판정·적합성 표·PR 본문이 인용하는 증거는 인용할 때 그 경로에 실제로 있고 관찰 대상을 잘림 없이 보여야 하며, 수치는 그것이 가리키는 실행의 산출물에서 그 실행의 식별자와 함께 인용합니다. 캡처한 증거는 덮어쓰거나 지우지 않습니다. 다시 돌리면 시도 번호를 붙인 새 파일에 쓰고 이전 것을 모두 남깁니다. 게이트가 고정 경로로 읽는 판정 파일만 예외입니다. PR 본문에는 전달한 행동, 돌린 테스트와 QA, 실제 한계에 더해 이 적합성 표와 계획의 COMPANION 행을 싣습니다. 리뷰 결과는 APPROVED 또는 REVISE이고, 막을 수 있는 이유는 목표 미달, 새 회귀, 잘못된 증거 세 가지뿐입니다. REVISE 수정은 지적된 사례나 문구만이 아니라 그 사례가 대표하는 결함 클래스 전체(예: 다른 ID를 지적했으면 같은 ID도)를 고치고, 재리뷰에는 직전 판정이 지목한 인터리빙·입력의 테스트가 수정을 되돌리면 실패하고 수정과 함께 통과하는 캡처를 냅니다. 증거는 대상별로 재사용 여부를 정하고, 모든 태스크가 merge된 뒤 마지막 보고 직전에만 병합 결과에서 전체 검증을 한 번 돌립니다. 세부 절차는 `references/verification.md`에 있습니다.

### 네이티브 스킬과 다른 점

wish는 네이티브 기본값 일부를 일부러 바꿉니다. 전체 표는 SKILL.md의 "Where wish specializes a native default"에 있고, 주요한 것만 추리면 이렇습니다.

- `/wish` 자체가 승인입니다. ulw-plan의 서약, 승인 대기, 별도 실행 세션은 없고 같은 세션에서 이어 갑니다. 계획 규율과 진짜 소유자 결정(되돌릴 수 없음, 파괴적, 비용) 질문은 그대로 남습니다.
- 계획은 `architect` 카테고리 한 라운드만 거칩니다. 차단 사항은 고치고 기록할 뿐 다시 리뷰하지 않으며, 네이티브 `plan-reviewer` 경로는 없습니다(아래 네이티브 plan 게이트 호환성).
- 루프 목표는 wish 전체에 하나입니다. 태스크와 런은 그 안에 삽니다.
- ultrawork처럼 RED를 먼저 쓰라는 규칙은 없습니다. 코드 먼저, 테스트는 그다음이라는 세 원칙을 따르고, 계획의 위험 목록이 어떤 회귀에 테스트를 달지 정하며, guard 테스트마다 회귀 주입 검사를 거칩니다(위 회귀 테스트).
- mass-ulw의 빠른 우선 사다리와 값싼 마무리 검증 노드 대신, wish는 난이도로 라우팅하고 호스트가 나열한 카테고리만 씁니다. 구현 배치마다 검증 노드를 하나 두고 그 배치에서 가장 어려운 노드 이상으로 두며, 다음 배치는 판정 파일로 게이팅합니다(위 태스크와 런).
- ultrawork는 확인할 조건마다 모니터를 걸어 기다리라고 하지만, wish에서 판정 게이트에 막혀 `BLOCKED`로 멈춘 노드는 판정을 기다리지 않고 바로 끝냅니다. 모니터·알람·폴링을 걸지 않으며, 그 일을 다시 맡길지, 언제 맡길지는 리드가 정합니다(위 태스크와 런).
- ultrawork는 재리뷰를 두 번까지만 하고 사용자에게 묻지만, wish의 REVISE 라운드는 APPROVED가 나올 때까지 횟수 제한이 없습니다. 소유자가 정한 정책입니다. 라운드마다 바뀐 부분만, 매번 새 리뷰어가 봅니다.

호환되는 나머지 네이티브 규칙(증거 수집, 정리 기록, 비동기 대기, 실패를 숨기지 않기, 검증 엄격함, 잡힌 회귀와 QA 실행 방법의 메모리 기록, 대상별 증거 재사용과 마지막 전체 검증 한 번)은 그대로 적용됩니다.

## 모드 동작

- `/wish`는 ultrawork가 켜져 있다고 보고 동작합니다. 꺼져 있으면 플러그인이 확장된 문장의 `ultrawork`/`ulw` 키워드를 보고 호스트 모드를 한 번 켜고 호스트 지시문만 붙입니다. 다른 요청의 `ulw`도 일반 모드를 켤 수 있지만, 그렇다고 그 요청이 wish를 쓰게 되지는 않습니다.
- 이미 켜져 있으면 상태를 그대로 두고 지시문을 다시 붙이지 않습니다. 미리보기는 모드 상태를 바꾸지 않습니다.
- 스킬 지침은 시스템·개발자 지시, 나중에 사용자가 명시한 요청, 도구가 실제로 막는 게이트보다 우선하지 않습니다. 엔진이 강제하는 규칙이 아니라 지침의 우선순위입니다.
- 호스트의 모드 연동을 쓸 수 없거나, 입력이 `before_agent_start`를 거치지 않는 경로(예: 대기열에 쌓인 입력)로 들어오면 플러그인이 모드를 켜지 못할 수 있습니다. 그때도 켰다고 말하지 않고, wish 스킬 지침대로 계속 진행합니다.

## 네이티브 plan 게이트 호환성

`/wish`는 호스트의 네이티브 plan-reviewer 게이트를 쓰지 않습니다. 그 게이트는 사용자가 ulw-plan 흐름을 명시적으로 요청했을 때처럼 호스트 조건이 맞을 때만 열리고, wish 계획에는 적용되지 않습니다.

- 계획 리뷰는 `architect` 카테고리 한 라운드로 끝냅니다. 지적된 차단 사항은 고치고 계획의 "Plan review record"에 기록하며 다시 리뷰하지 않습니다.
- 최종 ultrabrain 리뷰가 그 수정을 확인합니다.
- `architect`가 호스트 카테고리 목록에 없으면 멈추고 차단 사항으로 보고합니다. 대체 카테고리를 정하지 않습니다.
- 네이티브 plan-reviewer 경로는 없고, 게이트를 수동으로 풀거나 거부된 호출을 반복해서 재시도하지 않습니다.

```
│   └── wish.js                   # ultrawork 키워드로 호스트 모드를 켜는 확장
├── skills/
│   └── wish/
│       ├── SKILL.md              # 핵심 규칙과 단계별 로딩 지점
│       └── references/
│           ├── planning.md
│           ├── execution.md
│           └── verification.md
├── test/
│   └── wish.test.js              # 동작 테스트
└── scripts/
    └── verify.mjs                # 실제 호스트 로더로 확인하는 검증 스크립트
```

`package.json`의 `pi.skills: ["skills/wish"]`로 스킬이 호스트에 등록됩니다.

## 개발과 검증

```sh
bun test
bun scripts/verify.mjs .
```

`scripts/verify.mjs`는 설치된 Senpi의 실제 로더(프롬프트 템플릿, 스킬, 확장 러너)로 패키지를 불러와 확인합니다. 테스트와 검증기의 기본 Senpi 위치는 현재 사용자 홈 아래 `.bun/install/global/node_modules/@code-yeongyu/senpi`입니다. 다른 위치에 설치했다면 `SENPI_ROOT` 환경 변수로 설치 경로를 지정하세요.

## 커스터마이징

- 메뉴 설명과 진입 템플릿은 `prompts/wish.md`에 있습니다. 템플릿 문장에서 `ultrawork`와 `wish` 스킬 안내를 빼면 모드가 켜지지 않거나 스킬이 선택되지 않을 수 있습니다.
- 작업 규칙은 `skills/wish/SKILL.md`와 `references/` 파일에서 고칩니다. README는 설명일 뿐이니 규칙을 바꾸면 여기 요약도 맞춰 주세요.
